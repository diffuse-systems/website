Why on-premises

Capable hardware, and data that cannot leave

A university department has three hundred workstations that do nothing after six in the evening. A hospital has a rack it is not allowed to connect to the internet. Both are told the answer is a cloud cluster rented by the hour.

This runs the models on their own machines instead. CPU, GPU or a mix, several cooperating on one model when no single machine can hold it, and no prompt, no document and no corpus crossing the boundary. 

# two commands on the machine that coordinates
sudo apt install ./diffuse-coordinator_1.0.0_amd64.deb
sudo diffuse-coordinator licence set ./licence

# two on every machine that computes
sudo apt install ./diffuse-node-agent_1.0.0_cpu_amd64.deb
sudo diffuse-node-agent enroll --token DFE1-...

No script to run. No wheel to place. Nothing fetched at install.

How it works

Whole on one machine, or split across several

If a model fits on one machine in the pool it runs there, whatever its architecture. If it does not, the coordinator cuts it into slices, one per machine, connected as a pipeline.

Splitting has conditions, and they are checked before anything is downloaded rather than discovered afterwards. The documentation states them precisely, including what is refused and why.

Model support in detail

Serving qwen2.5-3b-instruct.

  placement   whole, in RAM
  reason      2.1 GB resident against 11.4 GB free
  context     4096

  slice 0   layers 0..36   node-01   2.1 GB   whole model

Placement says what it decided and why it decided it.

Built for audit

Built for the question an auditor will ask

Mutual TLS on every connection, with identity derived from the certificate rather than from anything a machine claims about itself. Roles, sessions and an append-only trail of who did what and what was refused.

Customer content never reaches that trail. Not prompts, not completions, not the rows of a training corpus. That is asserted by tests rather than promised. 

# who did what, and what was refused
diffuse-coordinator audit --since 7d

2026-08-23  alice   model.serve       ok
2026-08-23  alice   apikey.create     ok
2026-08-22  bob     node.revoke       ok
2026-08-22  ci      model.pull    refused  no machine has 11.8 GB free

Refusals are recorded as deliberately as successes.

Reasons for Diffuse

No activation. No heartbeat. No telemetry.

There is no call home of any kind. The licence is verified against a key already in the binary, on the machine, offline, for ever. An air-gapped deployment is the design rather than a concession to one.

This website holds itself to the same rule: no third-party font, no analytics, no tag manager, nothing embedded from anywhere else.

Getting started

From a bare machine to an answer

Four steps, and none of them is a support call. Everything is installed by the package manager and nothing is fetched when a node is given a model.

1

Install

One package on the machine that coordinates. It asks your organisation's name, generates the authority and starts.

apt install ./diffuse-coordinator…deb
2

Enrol

A token on every machine that computes. It writes an identity, starts the agent and waits to see it registered.

diffuse-node-agent enroll --token …
3

Serve

A name from the catalogue, or a file you already have. Placement says where it went and why.

diffuse-coordinator model run qwen2.5:3b
4

Call it

An OpenAI-compatible endpoint. Point an existing client at your host and give it your certificate.

POST /v1/chat/completions

Reasons for Diffuse

Against the obvious answer

The usual reply to "we want to run a model" is an hourly GPU instance. It is the right answer for a spike and a poor one for a department whose machines are idle sixteen hours a day.

A rented cluster

  • − Your prompts and your corpora leave the building.
  • − Per-token billing scales with curiosity, so people stop experimenting.
  • − A provider's policy change is your outage.
  • − The hardware you already own stays idle.
  • − "Where did this answer come from" has a long form.

Diffuse Enterprise

  • + Nothing leaves the deployment. There is no code that sends.
  • + You pay for machines, not tokens, whether you own them or rent them.
  • + A licence file, verified offline, with no activation call.
  • + Four ordinary machines hold a model none could, or one card holds it whole.
  • + Every action and every refusal on an append-only trail.

Common questions

Questions we get in the first meeting

Do we need GPUs?

No. A four-gigabyte model runs on an ordinary workstation with enough memory, and the CPU path is supported rather than tolerated. A card makes generation faster and lets one machine hold more.

How many machines do we need?

One, to start. Splitting a model across machines exists for models too large for any single one, and it is not the normal case.

Does anything leave our network?

No. No telemetry, no activation, no licence heartbeat and no usage report. The licence is verified against a key already in the binary, offline, for ever.

What happens when the licence expires?

Enrolling a new machine is refused. Nothing that is running stops and no request is interrupted. Software that stops working when a purchase order is late is software an operations team learns to fear.

Can we fine-tune any model we serve?

Fine-tuning needs the original safetensors weights, so a quantised file is refused at creation with the two ways to obtain trainable ones.
